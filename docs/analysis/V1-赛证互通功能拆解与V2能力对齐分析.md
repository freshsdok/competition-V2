# V1 赛证互通功能拆解与 V2 已实现能力对齐分析

## 1. 文档定位

本文基于 Repository 当前源代码，对 V1“赛证互通”功能进行事实拆解，并与 V2 已实现的 Credential、Competition Award、Eligibility、Commerce、Artifact/File 及多端页面能力对齐。

本文是功能说明和迁移分析，不是新的领域设计，也不把 V1 模型作为 V2 事实源。

核查快照：

| 项目 | Repository | 分支 | Commit |
|---|---|---|---|
| V1 参考实现 | `deshi_competition_2` | `empty-repo` | `4b380e7f0cddb7e72cad21332b3dcd495a26a2e3` |
| V2 当前实现 | `deshi_competition_v2` | `deshi_mac` | `651aafdda4dce22720769090efac309957c63d24` |

本次只进行了静态代码、SQL、API、页面及已有测试证据核查，未连接 V1/V2 运行数据库，未重新执行全量测试。因此本文中的“已实现”表示 Repository 中存在可追踪的实现链路，不等同于生产验收通过。

## 2. 一句话功能定义

V1“赛证互通”允许运营人员配置“用户已持有的源证书”到“可申请的目标证书”的兑换规则，系统核验用户证书、计算差额费用、创建兑换申请和支付订单；同时提供申请管理、证书发放/导入、我的证书、证书查询、预览与批量下载等配套能力。

从用户视角，主链路是：

```text
浏览互通规则
→ 阅读申请说明
→ 登录并完成实名认证
→ 系统核验源证书和持有年限
→ 选择目标证书
→ 计算兑换费用
→ 防重复校验
→ 创建兑换申请和支付订单
→ 支付结果回写申请
→ 后续获得并查看目标证书
```

## 3. 功能边界

### 3.1 核心“赛证互通”能力

1. 源证书与目标证书配置。
2. 互通规则草稿、发布、撤销、排序、首页展示。
3. 用户源证书匹配与持有年限判断。
4. 源证书组合条件（且/或）。
5. 证书分值和差额费用计算。
6. 兑换申请、重复申请检查和支付下单。
7. 支付、发票状态回写。
8. 用户与运营端申请查询、筛选、导出。

### 3.2 同一菜单下的相邻能力

以下能力与赛证互通共享证书数据或页面入口，但不是“兑换规则”本身：

- 赛事获奖证书配置和批量颁发；
- 历史/外部证书导入；
- 我的证书聚合展示；
- 公共证书查询；
- 负责人名下学生证书预览、缺图补偿和异步打包下载；
- 证书图片缓存同步。

迁移到 V2 时必须分别确认 Fact Owner，不能继续作为一个“大证书模块”整体搬迁。

## 7. V1 数据与规则模型

| V1 表/对象 | 业务作用 | 关键字段或关系 |
|---|---|---|
| `competition_cert_exchange_rule` | 互通规则主表 | 规则名称、赛事/阶段/赛道/组别、且/或、发布状态、排序、首页展示、版本 |
| `cert_exchange_rule_detail` | 源到目标的规则明细 | 源/目标证书配置、双方分值、源持有年限；多源×多目标展开保存 |
| `cert_config_info` | 可选证书配置 | 来源、赛事、赛道、组别、奖项、颁奖机构、管理员 |
| `competition_cert_exchange_apply` | 用户兑换申请 | 用户、规则、源/目标证书 ID 串、金额、订单、支付、发票、申请状态 |
| `user_certificate` | 当前用户证书记录 | 证书编号、URL、获证人、赛事、奖项、用户等 |
| `user_certificate_origin` | 历史/外部来源证书及收件人绑定 | 字段与用户证书高度重叠 |
| `user_certificate_history` | 证书历史数据 | 用于历史证书来源和状态保留 |

“我的证书”SQL 使用 `UNION ALL` 聚合 `user_certificate` 与 `user_certificate_origin`，并按 `user_id`、身份证号、时间和关键词过滤。因此，V1 用户看到的是两个物理事实源的合并结果，不是单一证书生命周期投影。

### 7.1 资格判断

V1 以当前登录用户实名信息中的姓名和解密后的身份证号查询 `user_certificate`，再追加赛事系列、阶段、赛道、组别和奖项条件：

- 未查到匹配证书：`无此证书`；
- 查到证书但持有年限不足：`拥有年限不足 N 年`；
- 全部或选定源证书满足：目标证书 `可兑换`。

### 7.2 费用计算

当前实现采用：

```text
源证书总分 = 所选源证书分值之和
目标证书总分 = 所选目标证书分值之和
总费用 = max(目标证书总分 - 源证书总分, 0)
单个目标费用 = 目标证书分值 - 源证书总分
```

代码把“分值”直接作为金额差使用，没有独立的价格版本、币种、计价策略快照或舍入策略。

### 7.3 申请与支付

V1 使用 Redis 分布式锁减少同一用户、同一规则的并发下单，然后查询订单状态：

- 存在 `PENDING`：阻止再次下单；
- 存在 `PAID` 且源/目标证书组合相同：阻止重复兑换；
- 校验通过：创建 `commodityType=cert` 的订单并保存申请为待支付。

支付和发票结果通过内部 API 回写 `competition_cert_exchange_apply`。

## 8. V2 已实现能力对齐

V2 没有复制 V1 的“赛证互通大表模型”，而是把用户能力落在多个明确的 Fact Owner 中。

| V1 用户能力 | V2 已实现能力 | 主要实现位置 | 对齐状态 |
|---|---|---|---|
| 配置证书类型 | Credential Definition + immutable Definition Version | `CredentialGovernanceController`、`V2_40_400__credential_ecosystem_core.sql` | 已实现，语义更明确 |
| 配置颁发机构 | Credential Issuer + Authority Version + Delegation | Credential Governance/Ecosystem | 已实现 |
| 配置源→目标互通规则 | Conversion Program + immutable Version | `CredentialEcosystemController`、`CredentialEcosystemApplicationService` | 已实现 |
| 发布可办理互通服务 | Conversion Offering：DRAFT/ACTIVE/PAUSED/RETIRED | Credential Ecosystem | 已实现 |
| 且/或/阈值条件 | Eligibility Policy：ALL_OF/ANY_OF/MIN_COUNT + typed requirements | Credential Ecosystem | 已实现，但不是 V1 任意分值袋 |
| 核验源证书 | 按当前 Subject 的 ACTIVE Credential Issue 和精确 Definition Version 匹配 | `opportunities()`、`source()` | 已实现 |
| 展示满足/缺失条件 | Opportunity：satisfied/missing requirements、next action | Web/Mobile“可办理的凭证互通” | 已实现 |
| 免费申请 | Application → Eligibility → AUTO/HUMAN_REVIEW → Issue | `apply()`、`approve()` | 已实现 |
| 收费申请 | Application → PAYMENT_REQUIRED → Mall Offer/Order → Credential Owner final recheck/issue | `CredentialConversionCommerceCapability`、Mall binding | 已实现代码链路 |
| 防重复申请 | `(conversion_offering_id, subject_id)` 唯一约束 + Idempotency-Key | Migration + Application Service | 已实现 |
| 目标凭证签发 | Credential Issue + exact governance link + issuance entitlement | Credential Ecosystem/Award | 已实现 |
| 我的证书 | 我的 Credential、展示 View、Award Entitlement、Wallet | Web `/me/credentials`、Mobile `/pages/credential/index` | Web/Mobile 已实现 |
| 获奖结果转凭证 | Competition Award → Credential Entitlement → Issue | `CredentialAwardController` | 已实现 |
| 撤销/替代/更正/补发 | append-only lifecycle event + issue lineage | Credential Award/Ecosystem | 已实现 |
| 公开证书查询 | opaque token 最小披露核验接口 | `GET /api/v1/public/credential-verifications/{token}` | Controller/API client 已实现；当前安全配置未把该路径放入匿名白名单，且未发现公开前端页面，故匿名产品闭环未完成 |
| 证书展示样式 | Credential View | `CredentialController` + Admin/Web/Mobile | 已实现基础能力 |
| 证书正式文件 | Issue 可引用 Artifact Version | Award issue API | 基础引用已实现；需按具体签发流程验收文件闭环 |
| V1 历史证书迁移 | V1→V2 mapping/quarantine 方案 | `docs/architecture/root-model-correction/historical-data-mapping` | 仅有映射与受控迁移准备；不能视为全量权威迁移完成 |
| V1 证书图片缓存/负责人批量下载 | V2 Artifact/File derivative + 授权下载应承接 | 当前核查未发现等价产品闭环 | 待补齐/待确认 |

## 9. V2 当前用户闭环描述

### 9.1 用户发现互通机会

```text
登录 Subject
→ 打开“我的证书与证明”
→ 系统读取当前 Credential Wallet
→ 读取已激活 Conversion Offering
→ 以精确 Definition Version 和 Eligibility Policy 逐项判断
→ 展示已满足条件、缺失条件、签发机构、价格状态和下一步
```

系统不会仅因用户拥有某个显示名称相似的证书就判定可互通，也不会自动替用户创建申请。

### 9.2 免费互通

```text
用户点击“立即申请”
→ 创建唯一 Conversion Application
→ 重新校验源 Credential 和 Eligibility
→ AUTO：批准并签发
   或 HUMAN_REVIEW：进入待审核
→ 新 Credential Issue 进入 Wallet
```

### 9.3 收费互通

```text
用户点击“申请并去付款”
→ 先创建 PAYMENT_REQUIRED Application
→ 跳转 Mall Offer
→ 支付成功保留 Commerce 事实
→ Mall 调用 CredentialConversionCommerceCapability
→ Credential Owner 重新核验来源凭证和规则
→ 签发目标 Credential
→ Mall 记录 fulfillment 结果
```

“支付成功”不直接等于“已经发证”，避免把 Commerce 变成 Credential 事实源。

### 9.4 凭证生命周期

V2 对撤销、替代、更正、续期和补发建立显式事件与血缘。旧凭证不会被直接覆盖，历史仍可解释；消费方是否认可某凭证，由具体 Context 下的 Trust Policy/Recognition Decision 决定。

## 10. V1 与 V2 的关键语义差异

| 主题 | V1 | V2 |
|---|---|---|
| 人员主键 | `user_id`，部分匹配依赖姓名+身份证号 | Subject 是统一主体；Credential holder 为 Subject |
| 证书事实 | `user_certificate`、`origin`、`history` 多表并存 | Credential Issue 为签发事实，Event/Lineage 保留历史 |
| 规则版本 | 主表有 `version`，规则更新时删除旧明细后重建 | Definition/Policy/Program/Conversion 使用不可变 Version |
| 资格判断 | 规则服务直接查证书表并比较字符串字段 | typed Eligibility 从各 Fact Owner 读取证据 |
| 收费 | 分值直接计算差价，申请服务调用订单服务 | 互通规则不保存价格；收费由 Mall Offer/Commerce 拥有 |
| 发证 | 支付回写与证书生成逻辑曾耦合；部分生成代码已注释 | Credential Owner 在支付证据后 final recheck 并签发 |
| 并发 | Redis 锁 + 查询后插入 | Idempotency claim + 数据库唯一约束 + optimistic transition |
| 公开验证 | 可按人、单位、证书编号查询较多信息 | opaque token 最小披露，降低枚举和隐私风险 |
| 权限 | 菜单/接口权限与业务数据混合 | Credential 不授予 Role/Permission；授权实时读取 |
| 文件 | 业务记录保存 `cert_url` | 正式文件应引用 immutable Artifact Version/File Object |

## 11. V1 代码风险与迁移注意事项

### 11.1 P0/P1 级风险

1. **敏感信息进入日志**：资格核验会解密身份证号，并将包含用户证书查询条件和结果的对象序列化到 INFO 日志。迁移时不得保留该行为。
2. **客户端可参与计价输入**：费用 API 接收前端回传的源/目标证书分值并直接计算，服务端没有在该方法内根据已发布规则重新加载权威分值。
3. **数据库唯一性不足**：重复兑换主要依赖 Redis 锁与“先查询再插入”；当前核查未发现对“规则+用户+源/目标组合”的数据库唯一约束。
4. **乐观锁不完整**：Mapper 虽将 `version=version+1`，但 UPDATE 条件未带 `version = oldVersion`，不能构成真实 optimistic lock。
5. **回写定位过宽**：支付结果更新按 `rule_id + user_id`，未强制锁定唯一申请/订单，存在误更新同一用户历史申请的风险。
6. **支付与发证不闭环**：支付回写方法中的目标证书生成代码已被注释；仅凭现有代码不能证明“付款后必然签发证书”。

### 11.2 结构性风险

- `competition_cert_exchange_apply` 同时保存申请、计价、订单、支付和发票状态，形成跨域状态聚合。
- 源/目标证书 ID 以逗号分隔字符串保存，缺少类型化关系和数据库参照完整性。
- 规则修改采用删除旧明细再新增，历史申请无法天然冻结当时使用的规则版本。
- `user_certificate` 与 `user_certificate_origin` 字段高度重叠，并由 `UNION ALL` 拼成用户视图，可能重复展示且事实来源难解释。
- 业务表和页面直接使用永久 `cert_url`。
- 管理端允许通用 CRUD 直接编辑、删除证书与申请状态，缺少明确业务 Command。
- 公开按姓名/单位查询证书可能产生人员枚举和隐私暴露，需要按数据公开政策重新评估。
- PC 富文本使用 `v-html` 展示申请说明，必须确认 CMS 输出经过可信清洗，防止存储型 XSS。

## 12. 不应直接迁移的 V1 行为

以下内容只能作为需求线索，不应原样搬入 V2：

1. 以姓名+身份证号作为证书持有人主关联方式。
2. 将“赛、证、支付、发票、文件”放在一个申请聚合中。
3. 把证书显示名称、赛道名称或奖项字符串作为稳定业务判断依据。
4. 使用源/目标证书 ID 字符串列表代替关系表。
5. 付款成功后直接推定目标凭证已经签发。
6. 通过 Credential 获得 Role、Permission、Participation 或 Qualification。
7. 把可变 URL 当作正式证书材料。
8. 用 Redis 锁或 SELECT-then-INSERT 代替数据库唯一约束。
9. 用当前规则、当前组织关系或当前资格重新解释历史申请。

## 13. 尚未完全对齐的产品能力

| 公开凭证核验闭环 | Controller 路径名为 `public`，但当前 Gateway/应用安全白名单未开放该路径，且未发现 Web/Mobile 匿名页面 | 建立独立 Public Verification 产品 Slice，补齐匿名路由、安全限流、最小披露和防枚举测试 |

## 14. 推荐的验收用例

### 14.1 V1 行为保真用例

1. 用户无源证书时看到明确缺失条件。
2. “且”规则缺少任一证书时不可申请。
3. “或”规则满足任一证书时可选择对应来源。
4. 持有年限不足时展示具体原因。
5. 已有待支付申请时不重复创建订单。
6. 已支付相同来源/目标组合时不重复申请。
7. 用户能在“我的证书”查看新签发结果。

### 14.2 V2 架构一致性用例

1. 同名但不同 Definition Version 的凭证不能误匹配。
2. 过期、撤销或被替代的来源 Credential 不可用于新申请。
3. 收费申请必须先形成 Application，再进入 Mall；付款后由 Credential Owner 重新校验。
4. 并发重复申请只产生一个有效 Application/Issue。
5. Human Review 模式不能被支付或前端参数绕过。
6. Credential 签发、撤销和互通不得新增 RoleAssignment 或 Permission。
7. Artifact 被替换时历史 Credential 仍引用原 Artifact Version。
8. 公开核验只返回批准的最小字段，未知 token 不泄露主体是否存在。
9. Web、H5、mp-weixin 对相同 Opportunity 状态和错误码展示一致。

## 15. 结论

### 事实

- V1 已形成面向 PC 的完整赛证互通申请链路，并具有规则配置、申请管理、支付衔接、证书查询/导入/下载等较丰富的运营功能。
- V1 小程序主要覆盖“我的证书”和互通订单展示，未发现与 PC 等量的完整互通申请页面。
- V2 Repository 已实现 Credential Definition、Issuer/Authority、Eligibility、Conversion Program/Offering/Application、Wallet、Award Entitlement、Mall 收费衔接、生命周期和 Trust/Recognition 等核心能力，并提供 Admin、Web、Mobile 页面入口。
- V2 尚不能仅凭本次静态核查宣称匿名公开核验、负责人批量下载、证书图片衍生物和 V1 全量历史证书迁移已经闭环。

### 推理

V2 已覆盖 V1“用户发现互通机会—提交免费/收费申请—审核或付款—签发目标凭证—进入我的钱包”的主业务目标，而且数据所有权、版本冻结、幂等与历史解释能力明显强于 V1。下一步不应重新复制 V1 模块，而应补齐产品入口和迁移证据。

### 风险

最大的风险不是“V2 少一张赛证互通表”，而是迁移时把 V1 的姓名/身份证匹配、双证书事实源、客户端计价、支付即发证、永久 URL 和弱并发控制一并带入 V2。任何历史导入都必须先区分来源事实、持有人绑定、签发事实、文件材料和互通申请，并对不确定记录隔离处理。
