## 流程

1. V1 `/system/teamCollectionNative/mine` 从既有授权名单读取当前登录人的队伍，决定新标签可见性。
2. 通过既有 `teamCollection/{id}/start` 取得队伍办理权，原短事务及版本并发控制不变。
3. 新的 `teamCollectionNative/{id}/entry` 在本地短事务中再次核对本人办理权与 version，生成30分钟有效的加密身份意图，返回固定 iframe 地址。此事务没有 V2 HTTP 调用。
4. 独立 V2 页面 `/v2-native/native-settlement#intent=...` 读取并立即移除片段，意图只保存在 iframe 的内存。
5. 没有新版原生会话时，跳转既有 `/login?returnTo=/native-settlement`。未认领人员选择“原账号 / 密码”，既有认领事务负责验证、认领、激活及密码升级；已认领账号正常登录。
6. 已有会话也必须核对其 Account、Subject 与当前 V1 用户的既有迁移绑定。错误账号不能呈现收款组件，用户可以显式退出新入口账号后重新登录。
7. 核对通过后直接渲染既有 `SettlementProfileView.vue`。保存、修改、提供给租户、敏感操作再验证都继续使用原业务接口。
8. 用户回 V1 点击“我已完成填报”，记录“办理人确认完成”、姓名与时间，供队友查看；放弃则复用原接口释放名额。

这不是免密码自动激活。激活依然需要用户通过 V2 既有登录证明。未绑定手机可以走原账号/密码，再使用当前密码完成安全验证；原银行卡表单仍要求收款联系手机号，此字段不是账号绑定手机号。

## 身份与会话隔离

- `/v2-native/`：独立 V2 Web 构建，开发端口5177；原5173、旧嵌入5176保持原路径。
- `/v2-native-api/api/v1/…`：仅放行新流程所需登录、协议、安全验证、本人收款资料和身份核对 API；不放行管理员、内部签发或其他业务接口。
- 新 Cookie 为 `V2_NATIVE_SESSION`、`V2_NATIVE_XSRF`。代理将其映射为 V2 原 Cookie，过滤 V1 与旧入口 Cookie、Authorization 和小程序标头；响应 Cookie 再映射回来。新登录/退出不覆盖旧入口 Cookie。
- 共用已有服务端 `V1_V2_INTERNAL_BRIDGE_HMAC_SECRET`，以独立用途派生 AES-GCM 密钥。意图不承载密码、银行信息，不创建 Session，也不提高 Session 保证级别。V1 userId 在浏览器中是密文。
- V2 新过滤器仅对带新意图标头的收款请求进行附加校验。新代理对相关路径强制要求标头；每次读取、保存、提供均核对来源绑定，防止其他标签页切换 Cookie 后串号。原请求没有该标头，仍走原有规则。
- 意图30分钟过期，前端每15秒重新核对；过期需要返回 V1 继续填报，重新获取入口。刷新 iframe 会丢失内存意图，需要从 V1 重新进入。
- 只支持同源代理部署，不把用户密码交给 V1 Java 服务，也不向 V1 数据库保存银行卡信息；代理只流式转发请求。

## 本地启用步骤

1. 保持之前的名单导入及 `V1_TEAM_COLLECTION_ENABLED=true`。本次不执行 SQL。
2. 在 **V1 teaching-system 的现有启动配置**中加入：

   ```dotenv
   V1_TEAM_COLLECTION_NATIVE_ENABLED=true
   ```

   保留已有服务端 `V1_V2_INTERNAL_BRIDGE_HMAC_SECRET`，禁止把该密钥放入 `VITE_` 配置或提交到仓库。修改后用原启动方式重启 teaching-system。

3. 在 **V2 platform-app 的现有启动配置**中加入：

   ```dotenv
   V1_V2_NATIVE_SETTLEMENT_ENABLED=true
   ```

   同时检查既有 `AUTH_PASSWORD_ENABLED=true`，需要认领未激活账号时，既有 `AUTH_LEGACY_CLAIM_ENABLED` 必须已按业务范围启用。V1、V2服务端上述共享密钥须相同且至少32字符。保持既有密码、迁移资格与安全验证策略，不直接改账号状态。

   用原启动方式重启 platform-app。重启前核对其实际 DB_URL 和 profile；本任务核查时运行中的 V2 使用远程业务库，因此本次没有代为重启 V2、执行迁移或做真实认领。

4. 启动新的独立 Web 进程，保留原 Web/embedded 进程：

   ```sh
   cd /Users/wwang/Documents/ClaudeCode/deshi_competition_v2/frontend
   pnpm dev:web:native
   ```

   默认端口5177、base `/v2-native/`，必须从 V1 同源入口访问，直接打开5177不作为完整流程入口。

5. 重启或让 V1 PC 的 Vite 自动载入新配置。默认代理已配置为：

   | V1 路径 | 目标 |
   | --- | --- |
   | `/v2-native/` | `http://127.0.0.1:5177` |
   | `/v2-native-api/` | V2网关 `http://127.0.0.1:8080`，转发时移除此新增前缀 |

   需要调整时在 V1 PC 的本地环境设置 `VITE_V2_NATIVE_WEB_TARGET`、`VITE_V2_NATIVE_API_TARGET`。若 V2 改过 Session Cookie 名称，还要配置 `VITE_V2_NATIVE_SESSION_COOKIE_NAME`。默认名称是 `DESHI_SESSION`。

   V2 既有允许来源配置须包含实际 V1 origin，例如 `http://localhost:8082`；`application-local.yml` 已包含该来源。保留 CSRF/Origin 保护，不用放宽为通配符。HTTP 本地测试需使用既有非 Secure Cookie 配置；生产维持 HTTPS/Secure。

6. 使用名单内正式学生登录 V1，刷新 `/personal/list`，应只看到“我的收款信息v2”标签。新标签可见需两个 V1 开关均启用、当前账号在已发布学生名单内。`mine` 返回空优先检查开关及原名单，不重新导入来绕过配置问题。

## 必须保留的业务边界

“办理人确认完成”是V1人工声明，不等于V2成功回执。保存资料与提供给指定租户仍为V2原有的两个动作，不会由V1自动替用户同意提供。

队伍状态控制的是V1办理入口。沿用当前约定，V1放弃/确认不会撤销V2原生Session，也不会删除已经保存的资料；已签发意图也不是实时查询V1队伍状态的凭证，在其有效期内不会因V1放弃而立即服务端失效。V1页面会随状态更新关闭iframe，但不能把关闭页面宣称为V2强制撤销。若未来要求“放弃之后，所有旧页面及直接API请求立即不可保存”，需要单独增加V1状态回查或撤销机制，不能仅靠iframe关闭实现。本次没有把V2本人资料变成队伍所有或新增提交后禁止修改规则。

## 回退

关闭 V1 `V1_TEAM_COLLECTION_NATIVE_ENABLED` 并重启teaching-system可隐藏新入口；同时关闭 V2 `V1_V2_NATIVE_SETTLEMENT_ENABLED` 可立即拒绝带新意图的资料请求（需配置生效/重启）。停止5177或静态新目录/5180适配器只影响新路径。保留原 `V1_TEAM_COLLECTION_ENABLED`、旧桥接配置与旧代理。

不要删除共享队伍表、事件或人工确认数据，不因停止新入口自动释放正在办理的队伍。新旧入口共享的办理人可通过原有放弃功能正常释放。
