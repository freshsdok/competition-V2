# 现场证件模型三方案决策评审

撰写时间：2026-07-04

本文件比较三种现场证件模型。本轮只做设计决策评审，不修改代码、不改数据库、不清理数据。

## 1. 三个方案定义

### 方案 A：保留当前双证自动生成

赛场发证时：

1. 自动确保一张 `COMPETITION` 大赛级证件。
2. 再生成一张 `SCHEDULE` 赛场级证件。

用户端表现：

```text
顶部大赛证 + 下方赛场证件
```

### 方案 B：取消自动大赛证，只生成 SCHEDULE 证件

赛场发证时：

1. 不自动生成大赛级证件。
2. 只生成 `SCHEDULE` 赛场级证件。

大赛级证件只通过直接发证页面生成。

用户端表现：

```text
以赛场证件为主；如果有直接发证的大赛证，再展示大赛证
```

### 方案 C：一证多权，核心证件 + 赛场权限 grant

赛场发证时：

1. 确保主体在大赛中有一张核心现场证件。
2. 不再为每个赛场生成新的实体证件。
3. 给核心证件写入一条 `SCHEDULE` grant。

用户端表现：

```text
一张核心二维码 + 多个赛场权限
```

## 2. 维度比较

### 2.1 产品理解成本

| 方案 | 评价 |
| --- | --- |
| A 双证自动生成 | 用户会看到“大赛证”和“赛场证”，需要解释为什么一次发证有两张证。 |
| B 只生成 SCHEDULE 证件 | 容易理解为“每个赛场一张证”，但不符合“一个主体一张核心证”的新思路。 |
| C 一证多权 | 用户只看到一张证，赛场是权限列表，最接近现实证件体验。 |

结论：C 最低，A 最高。

### 2.2 数据一致性

| 方案 | 评价 |
| --- | --- |
| A | 两张实体证件同时存在，主体字段、状态字段、快照字段容易漂移。 |
| B | 数据比 A 简单，但同一主体多赛场仍会多张 SCHEDULE 证件。 |
| C | 证件身份集中在 credential，赛场授权集中在 grant，状态集中在 operation_state，边界最清楚。 |

结论：C 最优。

### 2.3 删除 target 逻辑

| 方案 | 评价 |
| --- | --- |
| A | 删除 target 时需要同时处理 SCHEDULE 证件和自动大赛证来源，复杂且易残留。 |
| B | 删除 target 只需删除或撤销 SCHEDULE 证件，简单。 |
| C | 删除 target 撤销对应 SCHEDULE grant，不删除核心 credential，最符合生命周期。 |

结论：B 简单，C 更正确。

### 2.4 多角色人员

| 方案 | 评价 |
| --- | --- |
| A | 同一 user 可能被复用到错误的大赛证，参赛者/工作人员/专家角色容易互相污染。 |
| B | 多角色会表现为多张 SCHEDULE 证件或直接发证证件，展示和复用仍复杂。 |
| C | 一张核心证件可挂多条 role/scope grant，多角色由授权表达。 |

结论：C 最适合多角色。

### 2.5 报道和资料领取

| 方案 | 评价 |
| --- | --- |
| A | 大赛级证件天然适合报道和资料，但自动生成造成多证。 |
| B | 可由 SCHEDULE 证件触发 COMPETITION operation_state，但产品上“大赛报到”由赛场证触发略别扭。 |
| C | 核心证件天然支持大赛报到和资料领取，状态仍写 COMPETITION operation_state。 |

结论：C 保留 A 的优点，避免 A 的多证问题。

### 2.6 候场和资源预约

| 方案 | 评价 |
| --- | --- |
| A | 候场和资源预约主要靠 SCHEDULE 证件，能力明确，但实体证件多。 |
| B | SCHEDULE 证件天然适合候场和资源预约，但大赛核心身份弱。 |
| C | 候场和资源预约由 SCHEDULE grant 显式授权，不让大赛证天然拥有全部赛场权限。 |

结论：C 权限边界最准确。

### 2.7 PC / 小程序展示

| 方案 | 评价 |
| --- | --- |
| A | 当前已出现大赛级和赛场级混合展示，用户明显看到多证。 |
| B | 可以减少自动大赛证，但多赛场下仍可能多张赛场证。 |
| C | 一张主证件二维码 + 赛场权限列表，最适合用户端展示。 |

结论：C 最优。

### 2.8 历史数据兼容

| 方案 | 评价 |
| --- | --- |
| A | 最兼容当前代码，但继续累积当前问题。 |
| B | 需要处理已有自动大赛证，但 SCHEDULE 证件可继续沿用。 |
| C | 需要新增 grant 和迁移映射，兼容设计最复杂，但可以保留 legacy SCHEDULE 证件逐步过渡。 |

结论：A 短期最省事，C 长期最合理但要分阶段。

### 2.9 开发复杂度

| 方案 | 评价 |
| --- | --- |
| A | 修补复杂度中等：补来源字段、收窄复用、删除联动、前端分组。 |
| B | 开发复杂度较低：停止自动大赛证、调整展示、治理已有自动证。 |
| C | 初期复杂度最高：新增 grant 表、双写、扫码切换、前端重构、历史治理。 |

结论：短期 B 低，长期 C 更值得。

### 2.10 长期扩展性

| 方案 | 评价 |
| --- | --- |
| A | 实体证件越来越多，扩展新权限会继续叠加复杂度。 |
| B | 简化了自动大赛证，但仍把赛场权限绑定在实体证件上。 |
| C | grant 可扩展到候场、入场、资源预约、专家评审、工作人员、VIP、临时证。 |

结论：C 最优。

## 4. 方案 A 的适用条件

只有在以下条件同时成立时，才建议继续方案 A：

1. 产品确认用户需要同时看到大赛证和赛场证。
2. 每个主体多证是可接受体验。
3. 愿意补齐自动大赛证来源字段。
4. 愿意为删除、复用、多角色持续补规则。

当前不推荐继续 A，因为它会把现有问题制度化。

## 5. 方案 B 的适用条件

方案 B 适合作为短期止血方案：

1. 想快速停止赛场发证自动生成大赛证。
2. 暂时不准备引入 grant 表。
3. 可以接受一个主体多张 SCHEDULE 证件。
4. PC/小程序短期按赛场证件展示。

但方案 B 不是新产品思路下的最终模型。它只是从“双证”退回“赛场证件”，没有解决“一个主体一张核心证件”的目标。

## 6. 方案 C 的适用条件

方案 C 适合作为长期目标模型：

1. 产品希望用户看到一张核心现场证件。
2. 赛场、资源、专家、工作人员权限都要显式授权。
3. 报道/资料/候场等操作状态继续由 operation_state 承担。
4. 允许分阶段迁移，先双写和 fallback，再切换展示和停止旧实体证件。

方案 C 初期开发复杂度最高，但模型边界最清楚。

## 7. 推荐方案

推荐方案 C：一证多权，即核心证件 + 赛场权限 grant。

推荐理由：

1. 符合新的产品思路：一个主体原则上只有一张核心现场证件。
2. 保留大赛级身份凭证的直觉，天然支持报道、资料领取、身份核验。
3. 不让大赛证天然拥有全部赛场权限，避免候场、资源预约、入场权限扩大。
4. 删除 target 时撤销 grant，不删除核心 credential，更符合生命周期。
5. 多角色、多赛场、多资源可以通过多条 grant 表达，不需要叠加实体证件。
6. PC/小程序可以统一展示为“一张证 + 多个赛场权限”，用户理解成本最低。
7. 最大限度复用现有 operation_state：报道/资料仍写 COMPETITION，候场仍写 SCHEDULE。
8. 可以兼容已有 SCHEDULE 证件：先作为 legacy credential，再迁移为 grant，最后隐藏。

## 8. 推荐实施路线

不建议直接一步到位。推荐路线：

1. 阶段 0：只读审计和目标模型确认。
2. 阶段 1：新增 grant 表，双写 grant，不改变现有扫码。
3. 阶段 2：扫码 allowedActions 优先查 grant，兼容旧 credential。
4. 阶段 3：PC / 小程序改为一证多权展示。
5. 阶段 4：停用赛场发证生成 SCHEDULE 实体证件。
6. 阶段 5：历史 SCHEDULE 证件治理和隐藏。

这种路线允许每一步都回滚，避免破坏已通过的报道、资料、候场、代领和大赛级直接发证功能。

## 9. 决策注意事项

在进入开发前，需要产品确认以下问题：

1. 同一主体同一大赛是否绝对只有一张核心证件，还是不同身份可有不同核心证件。
2. 参赛者同时是工作人员或专家时，是否共用二维码。
3. 工作人员权限是大赛级授权，还是必须按赛场授权。
4. 资源预约是否只允许有 SCHEDULE grant 的主体使用。
5. PC/小程序是否接受“一张主证件 + 赛场权限列表”的展示文案。
6. 历史 SCHEDULE 证件隐藏后，管理端是否保留审计入口。

## 10. 本轮禁止事项确认

本轮不做：

1. 不修改代码。
2. 不改数据库。
3. 不清理数据。
4. 不执行 `UPDATE` / `DELETE`。
5. 不连接生产数据库。
6. 不删除旧 SCHEDULE 证件。
7. 不破坏已有 operation_state。
8. 不恢复临时混合模型作为长期方案。
9. 不使用伪赛场安排承载大赛权限。
