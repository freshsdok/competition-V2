# OpenOLAT 特点与对当前系统的借鉴

## 1. OpenOLAT 的主要特点

1. **服务端状态 UI 非常强**：复杂管理页面、表单、表格、树形课程结构都由服务器控制。
2. **业务模块按 Java 包高内聚组织**：Controller、模板、语言包、Spring 配置靠近业务包。
3. **资源仓库是核心主轴**：课程和内容资源不是散落对象，而是统一进入 RepositoryEntry/OlatResource。
4. **课程节点模型成熟**：课程由节点组成，每类节点承载一个学习活动或资源能力。
5. **用户组织权限较细**：Identity、User、Authentication、Group、Organisation、Grant、Policy 共同表达访问范围。
6. **企业集成丰富**：LTI、QTI、SCORM、WebDAV、会议系统、搜索、邮件、日历、通知等能力完整。

## 2. 对赛事系统最值得借鉴的部分

### 2.1 资源入口统一

可以把赛事、赛项、评审任务、证件模板、资源台账等抽象为统一 Resource 或 RepositoryEntry。这样收藏、权限、文件、发布、统计、归档可以共用一套机制。

### 2.2 流程节点化

赛事流程可以借鉴 CourseNode：

```text
赛事
  报名节点
  材料提交节点
  初审节点
  评审节点
  现场签到节点
  证件发放节点
  资源预约节点
  成绩发布节点
```

节点化比“每个流程写死在主业务代码里”更容易扩展。

### 2.3 服务端 UI 适合管理后台

对于赛事后台、配置、审核、评审、现场管理，服务端驱动页面能够降低前端复杂度。关键是把 Controller/模板/服务/权限组织在同一业务模块里。

### 2.4 组织/组/授权分离

不要只用 `user.role_code`。应考虑：

- 用户身份；
- 所属组织；
- 所属团队；
- 在某赛事的角色；
- 在某赛场的权限；
- 对某证件/资源/评审任务的授权。

## 3. 需要避坑的地方

| 风险 | OpenOLAT 表现 | 对本项目的提醒 |
|---|---|---|
| 服务端 UI 状态重 | 组件树保存在服务器 | 如果用户量和并发高，要谨慎使用重会话模型 |
| 模块很多但不等于插件治理 | 包很多、Controller 很多 | 必须有模块清单、表清单、权限清单，否则会失控 |
| 数据表自然增长 | 初始建表已超 300 张 | 当前项目已有两百多张表，更要控制表生命周期 |
| Java 企业架构偏重 | Spring/JPA/Velocity/自研 UI 框架复杂 | 不宜直接照搬，只借鉴分层和节点思想 |
| 多组织不是完整租户隔离 | Organisation/Group 权限治理 | 如果要 SaaS 租户，需额外定义 tenant 边界 |

## 4. 推荐落地路径

短期：建立赛事模块清单、资源入口清单、状态事实源清单、文件区域清单。

中期：抽象赛事流程节点，把报名、评审、证件、资源预约、现场核验做成节点化模块。

长期：建立统一 Resource/Scope/Grant/Event/File 模型，让业务模块通过统一骨架接入。
