## Execution order and bindings

Use a MySQL 8.0 prepared-statement client and the already verified connection/schema. `?` is a positional binding, not string substitution. Drivers using `%s` placeholders need a mechanical placeholder conversion; never interpolate values. Validate user-ID arrays as positive integers before binding. `JSON_TABLE` makes these queries MySQL 8.0 queries even though the V1 table migration also supports 5.7.

1. `01_v1_approved_award_candidates.sql`, on V1 `jiaoxue_test`: bind the JSON array of approved test-roster V1 IDs, the reviewed collection code, and the reviewed competition series ID. Returns their intersection with published, enabled award collection membership; only technical IDs, state, award level and identity-presence flags. The historical source configuration is `XINKE_13_2026` / series `81`, not evidence that the current database contains that cohort. An empty intersection does not itself authorize broader selection; the later user-authorized candidate check described above is a separate reviewed step, not a query or eligibility change.
2. `02_v1_latest_valid_identity_private.sql`, on V1: bind one selected approved test V1 user ID. Queries 02 and 05 can return a raw identity number. Keep their results private/in memory for the controlled test; do not print them or retain SQL result exports. An empty result or blank latest value is missing evidence, not authorization to choose a different person's number.
3. `03_v2_native_identity_candidate_state.sql`, on the actual V2 runtime database: bind the JSON array of technical V1 candidate IDs from step 1 or the separately user-authorized, reviewed selection documented above. This reads source provenance, current account/Subject lifecycle and available authentication-factor metadata. `READY_SOURCE_SNAPSHOT` does not prove login, factor usability, real SMS delivery, native intent validity, or browser acceptance. `HOLD` must not be repaired by flipping claim/account state for testing.
4. Optional `04_v2_historical_identifier_compatibility_private.sql`, on V2: bind the mapped Subject ID and the private identifier from step 2. Outputs counts/status only. It reproduces the frozen V1 historical fingerprint comparison; nonhistorical providers return `SERVICE_ADAPTER_CHECK_REQUIRED`. No active evidence is reported distinctly rather than treated as verified identity. Runtime identity validation remains the service's responsibility.

5. `05_v1_id_card_by_user_id.sql`, on V1: query-window alternative to 02. It uses `SET @v1_user_id = NULL` followed by a guarded SELECT of the latest passed, nondeleted identity record. The default NULL execution returns no identity. As recorded in [preflight-report.md](../preflight-report.md), the parent executed this default-NULL form in a read-only transaction against the current V1 database; it succeeded and returned 0 rows. This proves direct executability and unconfigured-input protection, not a particular identity value.

6. `06_v2_provision_metadata.sql`, on the verified V2 runtime database: four independent prepared SELECTs for reviewed tenant code/ID, the owner's current profile metadata, all access metadata for that owner, and new target-unit audit entries. Bind each statement separately as documented in the file. These statements deliberately exclude private profile fields and raw audit JSON. The author has not run them; the parent executed equivalent technical metadata reads supporting the provision and final-audit snapshots, not a verified literal execution of this file.
7. `07_v1_completion_metadata.sql`, on the verified V1 runtime database: two prepared SELECTs for team state and new events after a recorded event ID. The actual final action is `USER_CONFIRM`, with resulting status `USER_CONFIRMED_COMPLETE`; no mutation is included.
