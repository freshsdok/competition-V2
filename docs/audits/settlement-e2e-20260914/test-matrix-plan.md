## 事实、推理与边界

**事实（代码级依据）**：V1 按名单及当前团队办理人控制入口，状态为 `AVAILABLE` → `IN_PROGRESS` → `USER_CONFIRMED_COMPLETE`；主动放弃返回 `AVAILABLE`，操作带 version。V2 收款资料归本人 Subject 所有，保存资料与向指定单位提供权限是两个动作。V1 顶部完成按钮需先读回 V2 当前资料与选定单位的 PROVIDED 版本，再核对 V1 当前办理权；点击最终按钮时重复核验。安全验证只在实际接口返回 `403 / STEP_UP_REQUIRED` 后出现。

**推理与实测范围**：设计路径为“本人登录 → 保存 → 明确提供 → 最终人工确认”，本轮样本已完成这条主线，并观察本人不匹配、队友阻止和撤销失效。旧版本、读回失败等剩余边界仍取决于真实样本、进程及配置，不能由源码或已完成主线直接判定通过。

**边界**：

- 无绑定手机号的账号可用已有 ACTIVE 密码验证；收款表单的“收款联系手机号”仍为必填字段，两者不同。当前验证组件也保留 ACTIVE 邮箱验证码因子。
- 不保证每次保存都出现短信验证：服务端要求新近且为 STRONG 的正式会话；新近验证窗口由实际运行配置 `stepUpTtl` 决定。需核实实际值并记录，不假定固定分钟数。
- native intent 自签发起最长30分钟，前端通常每15秒核对；不能把页面“继续填报”或刷新后新签发的入口当成原入口尚未过期。最终读回整体限时15秒，网络与响应体读取均计入。
- V1 的放弃、确认和关闭 iframe 不会即时吊销已签发 intent、退出 V2 Session、删除本人资料或撤销既有单位权限。团队入口互斥不等于 V2 本人资料自此不可修改。
- V1 完成仍是办理人声明；V1/V2 读回与完成写入不是跨库原子事务。服务端现有 confirm API 未增加“必须有 V2 回执”的强制约束。
- “已保存”“已提供”“办理人确认完成”都不表示银行验卡、获奖资格重新审批、发奖或到账。仅所选单位财务权限与提供关系共同决定财务访问；目录可见不等于已提供。

## 执行顺序与结果判定

1. 先完成环境记录、资格、已有账号匹配和不提交数据的界面检查。已获准读取真实数据仅用于核实身份/资格，不复制到手册。
2. 使用已授权的模拟银行卡资料、核实 D/T 实际样本后，执行表单负例、真实安全验证、保存、提供、撤销/重新提供、取消漫游、刷新恢复等可继续办理的分支。
3. 并发、其他账号、真实短信/邮箱、自然过期分别依赖对应样本或等待。与主线独立计证据，缺失就保留未执行，不能靠模拟替补。
