# Moodle 对当前教育/赛事系统的可借鉴点

## 1. 最值得借鉴的部分

### 1.1 上下文权限模型

Moodle 的 `context + role + capability` 适合借鉴到赛事系统中。当前赛事系统如果存在平台、赛事、赛程、赛场、团队、证件、资源等多层对象，可以建立统一作用域，避免每个业务域各自写权限判断。

### 1.2 插件化业务挂接

Moodle 用 `course_modules` 统一挂接课程活动。赛事系统可以借鉴为：赛事主轴表 + 业务模块实例表 + 模块类型注册表。这样报名、证件、资源预约、评审、现场扫码不必全部塞进赛事主表。

### 1.3 文件池定位方式

Moodle 文件表通过 `contextid + component + filearea + itemid` 统一定位文件归属。当前系统的文件交互、材料提交、评审材料、证件照片、导入文件都可以参考这种结构。

### 1.4 选课模型对“报名”的启发

`enrol` 和 `user_enrolments` 的分离可以映射到赛事报名：报名渠道/报名规则是一类配置，团队/个人报名事实是另一类事实。不要把报名方式和报名结果混在一张表中。

### 1.5 成绩册对评审评分的启发

Moodle 的 `grade_items + grade_grades` 可以启发评审：评分项定义和参赛对象得分事实分离，活动/评审任务只接入统一评分事实。

## 2. 不建议直接照搬的部分

| Moodle 设计 | 不建议直接照搬原因 | 建议做法 |
|---|---|---|
| 完整插件生态 | 对当前系统可能过重，开发约定成本高 | 只抽象少数稳定扩展点 |
| 全量 context 权限树 | 如果当前权限较简单，会增加复杂度 | 先做赛事/赛场/资源等关键作用域 |
| 课程活动模型 | 赛事不是课程，生命周期不同 | 借鉴“模块挂接”，不要照搬字段 |
| Moodle 文件池完整机制 | 实现成本较高 | 先统一文件归属字段和审计字段 |
| 大量插件表 | 表数量可能进一步膨胀 | 建立模块归属、命名和生命周期治理 |

## 3. 可落地改造方向

### 短期

1. 建立统一业务对象命名规范：`scope_type + scope_id` 或明确的业务外键。
2. 文件模块统一补充 `biz_type/biz_id/file_area` 或类似字段，减少附件表分裂。
3. 梳理用户在赛事、团队、赛场、证件、资源中的角色来源。
4. 对评审评分项、证件授权、资源预约建立唯一性和事实源说明。

### 中期

1. 建立“赛事模块实例”概念，承接报名、评审、资源、现场证件等子系统。
2. 建立统一授权/作用域模型，替代散落的 role_code、credential_type、operation 权限判断。
3. 建立统一事件日志，让现场扫码、状态变更、预约、支付、评审等操作进入一致审计模型。
4. 建立统一文件池或文件归属模型。

### 长期

1. 将赛事主数据、参赛事实、现场事实、资源事实、支付事实、评审事实分层治理。
2. 对历史临时表/导入表建立归档和冻结策略。
3. 逐步形成可插拔的业务模块，而不是继续堆叠特例表。

## 4. 总体建议

当前系统更适合“在现有基础上分层治理和模块化重构”，不适合直接照搬 Moodle 重写。Moodle 的价值在于提供成熟参照：上下文权限、统一文件池、插件注册、服务注册、成绩/评分事实模型、课程/活动挂接模式。
