# 得时综合教育平台项目整体代码与数据资产评估报告

评估日期：2026-08-16  
评估范围：当前仓库全部存量代码、当前未提交开发、数据库迁移、历史审计与需求文档  
评估方式：只读静态扫描、规模统计、关键链路抽样、现有审计材料交叉核对  

> 本次未执行构建、自动化测试、依赖漏洞扫描，也未连接生产数据库。数据库规模引用仓库中测试库 `information_schema` 的历史盘点结果；生产数据量、性能和真实数据质量需要另行采集。

## 1. 执行摘要

当前系统不是单一“赛事报名系统”，而是一个已经覆盖赛事全生命周期、现场执行、资源预约、评审、支付、文件、内容、流程、即时通信和多端访问的综合教育业务平台。系统的业务覆盖度较高，Java 17、Spring Boot 3.3、Vue 3 等基础技术栈仍具备继续演进的条件，近阶段新增的现场、资源、评审能力也形成了较完整的数据模型和文档资产。

主要矛盾是：业务复杂度已经达到平台级，但架构边界、数据事实源、测试体系、发布治理和数据治理仍处于项目型系统阶段。继续以当前方式叠加功能，会显著增加状态不一致、跨模块回归、并发重复、权限遗漏和数据迁移成本。

综合静态评分：**58/100，可持续运行，但应进入系统化治理期。**

| 维度 | 评分 | 结论 |
| --- | ---: | --- |
| 业务功能完整度 | 82 | 覆盖面强，是当前最主要资产 |
| 技术栈可演进性 | 75 | Java 17/Spring Boot 3/Vue 3 基线较好 |
| 文档与知识沉淀 | 78 | 反向需求、数据库、现场和评审文档较丰富 |
| 后端工程质量 | 62 | 分层存在，但核心 Service/Mapper 过大 |
| 架构与领域边界 | 58 | `competition`、`system` 持续吸收跨域能力 |
| 数据模型与治理 | 57 | 业务表丰富，但事实源、唯一性、租户边界不足 |
| 前端工程质量 | 55 | 三端能力完整，但页面过重、重复实现较多 |
| 安全与隐私治理 | 52 | 有权限框架，输入、富文本、配置和隐私治理不足 |
| 可观测性与运维 | 46 | 有 Actuator/监控基础，链路、指标、迁移治理偏弱 |
| 自动化测试 | 40 | 后端有局部测试，前端和关键集成链路明显不足 |
| CI/CD 与质量门禁 | 38 | 仓库未发现 CI、SCA、统一代码质量门禁 |

核心判断：

1. 不建议立即做物理微服务拆分。应先建立领域边界、统一状态和数据事实源，并补齐回归测试。
2. 未来平台升级的第一优先级不是重写页面，而是建立 `Tenant / Organization / Workspace / Member / Tool / Record` 平台骨架和数据迁移标准。
3. 当前最需要保护的资产是业务规则、历史数据、组织与参与关系、评审结果、证件与现场操作记录，而不是现有 Controller 或页面结构本身。
4. 当前未提交的教师赛匿名报名改动具备基本防护，但应解决手机号身份边界、跨赛事绑定范围和异步失败补偿后再发布。

## 4. 技术架构现状

- Java 17、Spring Boot 3.3.5。

- Nacos 服务发现/配置，Gateway 网关，Feign 服务调用。

- Seata 分布式事务组件、Flowable 工作流。
- OSS/MinIO、POI、JWT、Fastjson2、Knife4j/Springdoc。
- Actuator 和监控模块已存在，但业务指标与链路跟踪较弱。

### 4.2 前端

- 管理端：Vue 3、Vite 6、Element Plus、Pinia、ECharts、BPMN、文档预览。
- PC 端：Vue 3、Vite 4、Element Plus、Pinia、Tailwind、BPMN、表单设计器。

### 4.3 部署形态

仓库 Docker Compose 包含 Nacos、MySQL、Redis、Nginx、Gateway、Auth、System、Gen、Job、File 和 Monitor。当前没有发现 Flyway/Liquibase、Maven Wrapper、GitHub/GitLab/Jenkins 流水线或代码扫描配置。

架构总体仍可继续演进，但“微服务部署形态”领先于“领域边界和工程治理成熟度”。一些服务拆分是按技术或早期模板边界完成的，核心业务仍高度集中在 competition/system 两个模块。

## 6. 工程质量评估

### 6.1 值得保留的工程基础

1. 后端升级到 Java 17/Spring Boot 3，避免了在旧运行时上继续堆积技术债。
2. 已形成 Gateway/Auth/API/Common/Modules 的基本工程分层。
3. 扫描到约 915 个 `@RequiresPermissions`、97 个 `@InnerAuth` 和 599 个操作日志注解，说明权限和审计不是完全缺失。
4. 扫描到约 226 个事务注解，并在资源、证件、评审等新模块中开始使用唯一键、状态条件更新和幂等键。
5. 现场、资源、评审模块同时保留设计、迁移、实现和测试文档，知识可迁移性好于一般存量项目。
6. 管理端和 PC 端均有依赖锁文件，后端依赖版本主要由父 POM 统一管理。

### 6.3 测试现状

- 当前发现 48 个后端测试文件、约 484 个断言关键词。
- 其中 competition 24 个、system 11 个、content 4 个、common 6 个，其他模块极少。
- 已覆盖部分现场、证件、评审、资源和教师赛逻辑，这是正确方向。
- 认证、网关、支付、文件安全、通知可靠性和前端主链路覆盖不足。
- 没有发现统一 CI，测试是否执行取决于开发者本地操作。

应优先建立的回归矩阵：

1. 报名重复校验、团队成员变更、匿名报名账号绑定。
2. 资源预约并发创建/取消、容量扣减和释放。
3. 扫码核验、证件发放/撤销、active grant 唯一性。
4. 评审提交、退回、锁定、作废、汇总发布。
5. 支付回调和退款回调幂等重放。
6. 文件上传类型、MIME、大小、归属、病毒/压缩包策略。
7. 登录、报名、证件、预约、评审秘书等多端冒烟链路。

### 6.4 安全与隐私

- 权限框架覆盖较广，但接口权限、菜单权限和网关放行规则缺少自动对账。
- 29 个前端源码位置使用 `v-html`，需要统一经过可信 HTML 净化组件。
- 配置文件中存在密码/密钥类配置项；本次未展示和验证真实值，应迁移到环境变量或密钥管理系统。
- 身份证和手机号在代码/SQL 中高频出现，扫描分别命中约 491 和 648 次；敏感字段注解仅命中 1 次，表明脱敏、加密、访问审计仍未体系化。
- 需要建立个人信息分级、展示脱敏、导出水印、访问审计、保留周期和删除/匿名化策略。
- 当前没有可见依赖漏洞扫描、SBOM、容器镜像扫描和密钥扫描门禁。

## 7. 当前未提交开发专项评估

当前已跟踪 diff 涉及 26 个文件，约 `+557/-467`，主题为教师赛匿名报名、Excel 字段调整和注册后账号自动绑定。模板下载相关新增端点已移除，继续沿用原下载方式。

### 7.1 正向评价

- 内部绑定接口使用 `@InnerAuth`，没有直接暴露为普通匿名接口。
- 绑定更新带 `user_id is null` 条件，具备基础并发保护和重复调用幂等性。
- 候选记录按身份证号做歧义检测，多身份证时拒绝自动绑定。
- 绑定逻辑使用事务，报名表、成员表和团队表更新可共同回滚。
- 新增了教师赛 Excel 和绑定逻辑测试，且对 JSON 伪装 Excel、缺少学校等场景增加校验。

### 7.2 上线前风险

| 级别 | 风险 | 证据与影响 | 建议 |
| --- | --- | --- | --- |
| P1 | 手机号身份边界未形成明确合同 | 注册账号只需手机号命中，代码不再要求账号实名认证/教师身份与报名身份证一致 | 明确“短信手机号所有权即足够”是否为正式规则；高价值操作前补二次核验 |
| P1 | 查询和绑定范围跨全部赛事 | 查询仅按手机号、教师赛名称和状态过滤，没有 `competition_series_id`；同身份证会绑定所有历史记录 | 业务确认是否需要历史全量认领；否则增加赛事/时间范围或建立待认领确认流程 |
| P1 | 异步失败没有可靠补偿 | `@Async` 调用失败仅写 warn，服务不可用时用户会永久漏绑定 | 使用可重试任务/outbox，记录绑定状态、失败原因和人工补偿入口 |
| P2 | 业务语义依赖中文名称 | SQL 使用 `competition_track_name = '教师赛'` | 改用稳定类型码/赛道类型，不以展示名称判断业务 |
| P2 | migration 不可重复执行 | 直接 `ALTER TABLE ADD COLUMN` 和普通文件名，未接入 Flyway/Liquibase | 增加存在性检查、版本表、执行记录和回滚/前滚脚本 |
| P2 | 五列索引上线成本未评估 | MySQL 5.7 大表建索引可能锁表或产生较长 DDL | 上线前获取表行数、索引大小和执行窗口，必要时使用在线 DDL |

发布结论：**有条件发布**。至少需要确认手机号认领规则、绑定范围，并提供失败补偿方案；否则会产生难以发现的账号归属错误或漏绑定。

### 8.3 关键结构性缺口

#### 1. 缺少租户和业务空间主轴

源码和当前 migration 中几乎没有 `tenant_id`。现有数据主要通过 `competition_series_id`、`org_id`、`team_code`、`schedule_id` 横向连接，赛事在事实上承担了部分空间边界，但无法自然支持产业学院、培训项目、实训项目等新场景。

建议平台骨架：

```text
Tenant
  -> Organization / OrganizationMember
  -> Workspace / WorkspaceMember
  -> WorkspaceTool
  -> BusinessRecord / BusinessEvent
```

存量赛事可迁移为 `workspace_type = COMPETITION`，不必立即重写所有赛事表；先建立映射和统一访问上下文。

#### 2. 主数据、快照和事实源边界不清

组织名、角色名、组别名、赛道名等既可能是当前主数据，也可能是报名/证件/评审时点快照。升级时不能简单去重或全部改为外键，否则会破坏历史凭证。

建议规则：

- 当前可变信息使用主数据 ID。
- 历史业务凭据保留 `_snapshot` 字段。
- 当前状态使用唯一事实表或明确状态字段。
- 状态变化使用 append-only 事件/日志，不用日志反推当前状态。

#### 3. 业务唯一性不足

重点事实包括有效报名、团队成员、赛场 target、核心证件、active grant、operation state、有效预约、评审外部引用、支付流水。应先对历史重复做画像，再通过 `active_key`、条件唯一键或业务键约束治理。

#### 4. 状态和字典缺少注册表

`status`、`check_status`、`pay_status`、`cert_status` 等值分散在数据库、Java、XML 和三端前端，且存在 `CANCELED/CANCELLED` 等同义值。升级前应建立字段级枚举注册表：所属域、字段、合法值、含义、终态、可达迁移、兼容值、展示文案。

#### 5. 隐私和数据生命周期不足

身份证、手机号、学校、单位、评语、支付和文件数据具有不同敏感等级。目前需要补齐：采集目的、授权依据、最小访问范围、展示脱敏、导出控制、保存期限、归档和匿名化规则。

### 8.4 升级前必须采集的数据指标

当前静态仓库无法回答下列问题，但这些数据直接决定升级方案、迁移窗口和系统容量，应作为平台升级的第一批基线数据。

| 分类 | 必采指标 | 用途 |
| --- | --- | --- |
| 表规模 | 每表行数、数据/索引大小、月增长率 | 迁移批次、存储和 DDL 窗口 |
| 时间分布 | 最早/最新记录、年度/月度增量 | 冷热分层和归档 |
| 数据质量 | 空值率、重复率、非法枚举、孤儿关系 | 清洗和约束上线前置 |
| 核心唯一性 | 报名、成员、证件、grant、预约、评分、支付重复数 | 评估业务错误和修复成本 |
| 状态一致性 | 主表状态与日志/流程/支付渠道不一致数 | 确定真实事实源 |
| 身份质量 | 手机/身份证重复、共享、变更、未绑定比例 | 统一身份迁移策略 |
| 文件资产 | 文件数、总容量、类型、无引用文件、重复哈希 | OSS 迁移、成本和安全 |
| API 流量 | 接口 QPS/P95/P99、错误率、调用方 | 服务边界和容量设计 |
| SQL 性能 | Top SQL、扫描行数、锁等待、慢查询 | 索引和读模型设计 |
| 业务转化 | 浏览-报名-支付-参赛-评审-获奖漏斗 | 产品升级价值判断 |
| 现场运行 | 核验量、峰值、重复扫码、离线失败、设备分布 | 现场架构和离线能力 |
| 资源利用 | 容量、预约、取消、爽约、冲突、利用率 | 排程和资源优化 |
| 评审质量 | 分数分布、专家偏差、退回率、耗时、异常分 | 规则优化和质量控制 |

### 8.5 建议建立的平台级数据产品

1. 统一身份与组织目录：用户、多组织成员关系、外部身份映射、身份历史。
2. Workspace 参与者主表：统一表达参赛者、学员、教师、专家、导师、工作人员。
3. 业务事件中心：报名提交、审核、支付、签到、核验、评分、发证等标准事件。
4. 状态与规则注册中心：状态机、字典、规则版本和生效时间。
5. 数据质量看板：重复、孤儿、非法状态、对账差异、异步失败。
6. 运营分析模型：用户、组织、Workspace、活动、资源、评审、收入等主题域。
7. 审计与隐私台账：敏感字段、访问者、访问目的、导出记录、保留期限。

## 9. 平台升级建议

### 9.1 目标架构原则

1. 先模块化，再决定是否拆微服务。
2. 以 Workspace 统一赛事、产业学院、培训和实训项目，不再为每种业务复制一套用户、文件、流程和权限能力。
3. 业务写模型保持强一致和可审计，分析模型通过事件/CDC 构建。
4. 关键状态由数据库约束、条件更新和应用层幂等共同保证。
5. API 采用明确 DTO、错误码、版本和 OpenAPI 合同，三端共享生成类型或契约测试。
6. AI 只能辅助分类、摘要、推荐、异常提示，不能直接成为身份、成绩、支付、证件和评审结果的事实源。

### 9.2 领域边界建议

短期在现有模块内先形成包和应用服务边界：

```text
platform-core
  identity / organization / permission / workspace

competition
  catalog / registration / team / progression / award

onsite
  schedule / target / credential / verification / operation

review
  activity / rule / assignment / submission / scoring / result

resource
  catalog / deployment / slot / reservation

support
  file / payment / notification / workflow / content / audit
```

只有当独立扩缩容、独立发布、数据所有权和团队所有权都明确后，才把领域边界物理拆成服务。

### 9.3 分阶段路线

#### 0-30 天：建立可控基线

- 冻结状态字典继续无序新增，建立状态/错误码注册表。
- 为当前教师赛绑定补可靠重试、业务确认和对账查询。
- 建立 Controller 权限与菜单权限自动对账。
- 建立 CI：编译、单测、前端构建、静态检查、密钥扫描、依赖扫描。
- 将数据库 migration 纳入 Flyway/Liquibase 或等价版本表管理。
- 建立生产数据只读画像脚本和首版数据质量报告。

#### 1-3 个月：治理高风险链路

- 补齐预约、扫码、证件、评审、支付、文件的 P1 回归集。
- 治理 active 唯一键、状态条件更新和应用层幂等响应。
- 将超大 Service/Mapper/Page 按领域用例拆分，不改变部署边界。
- 建立统一富文本净化、文件安全、下载鉴权和隐私脱敏组件。
- 统一三端 API 错误处理、字典和下载上传合同。
- 接入 Trace/Metrics/业务告警，覆盖异步失败和跨服务调用。

#### 3-6 个月：建设平台内核

- 落地 Tenant、Organization、Workspace、WorkspaceMember 和外部身份映射。
- 将赛事作为首个 Workspace 适配，不立即迁移全部物理表。
- 建立事件表/outbox 与分析数据链路。
- 完成状态机、规则版本、快照字段和数据血缘治理。
- 建立订单/支付、证件/核验、评审/结果三类正式对账机制。

#### 6-12 个月：扩展与数据产品化

- 将产业学院、培训、实训、课程项目作为新 Workspace 类型接入。
- 建立统一参与者、能力评价、证书与学习成果模型。
- 建设运营分析、资源优化、评审质量和组织画像主题数据集。
- 根据真实流量、发布频率和团队边界决定服务物理拆分。

## 11. 最终结论

平台现有代码的最大价值是已经跑通并编码了大量真实复杂业务，特别是赛事报名、现场执行、证件、资源和评审链路。最大风险则是这些能力继续集中在少数大模块、大 Service、大 Mapper 和大页面中，数据状态、身份、权限和并发规则依赖开发者经验维持。

升级工作应采用“保护业务事实和历史数据，重建平台骨架与工程基线”的方式，而不是简单推倒重写。优先级应依次为：

1. 身份、组织、Workspace 和数据边界。
2. 状态事实源、唯一性、幂等和对账。
3. 自动化测试、CI/CD、迁移和可观测性。
4. 核心模块内部领域拆分和三端 API 合同统一。
5. 数据资产产品化和产业学院等新 Workspace 扩展。

在完成前两阶段治理后，当前系统具备平滑升级为多租户教育产业协同平台的现实基础；若跳过这些基础直接扩展新模块，技术和数据债务会以更高速度累积。
