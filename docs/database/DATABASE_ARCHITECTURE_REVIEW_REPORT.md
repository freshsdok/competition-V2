# 数据库架构总体评估报告

审计边界：本轮仅做只读审计和报告生成；测试库只查询 `information_schema`；未执行 UPDATE / DELETE，未连接生产库，未生成破坏性 migration。

## 1. 总体评价

当前数据库已经覆盖赛事、报名、赛场、证件、扫码、资源预约、评审、支付、文件、内容、用户权限等完整业务链路。总体设计可以支撑业务运行，但存在典型的快速迭代后遗症：主轴事实源不够集中、状态事实分散、同义字段多名化、泛化 `status` 过多、业务唯一性大量依赖代码。

## 3. 核心数据主轴

建议把主轴明确为：`赛事系列/赛事主数据 -> 报名团队/成员 -> 赛场 schedule/target -> 证件 credential/grant -> 现场 operation_state/log -> 资源 reservation -> 评审 object/material/score/result -> 支付/文件/内容支撑域`。当前多处通过 `team_code`、`competition_series_id`、`schedule_id`、`target_id` 横向连接，缺少统一的数据血缘说明。

## 4. 高风险一致性问题

- 同一团队报名、成员、赛场 target、核心证件、active grant、operation_state、有效预约等关键事实缺少可见业务唯一约束或约束不充分。
- 软删除和取消态没有统一 active 判定，导致补唯一键时必须先治理历史重复。
- 操作日志和状态表边界需要严格区分，日志不能被当作当前状态事实源。

## 5. 冗余字段和重复语义

- `competition_id`/`competition_series_id`、`team_id`/`team_code`、`role_code`/`competition_role_name`、`group_name`/`second_level_name` 等需要统一词汇表。
- 快照字段合理存在，但缺少 `_snapshot` 或注释时，容易被误用为主数据。

## 6. 缺失唯一约束

优先补充 active 唯一键的地方：证件实例、grant、operation_state、资源预约、slot group scope、resource schedule scope、review external ref、报名团队/成员。

## 7. 状态事实源问题

泛化 `status` 横跨配置启停、发布、审核、支付、预约、评审、证件等场景。建议建立统一枚举注册表，字段名按域拆分，历史值做兼容映射。

## 8. 快照字段问题

证件、预约、评审、操作日志、导入中间表中的快照是必要的；问题主要是命名和注释不足。新增字段建议采用 `_snapshot` 后缀，历史字段补 column comment。

## 9. 废弃/临时表问题

`offline_v3_*`、`offline_v4_*`、`*_copy1`、未被代码引用的表应先标记归属和冻结写入，不建议直接删除。Flowable 表即使业务代码未直接引用，也应视为框架运行表。

## 10. 近期优化优先级

1. 建立数据库字段词汇表和枚举注册表。
2. 对高风险事实表跑重复数据审计 SQL，只读确认重复规模。
3. 为 active 事实源设计唯一键方案，不立即落库。
4. 给快照字段和历史兼容字段补注释。
5. 标记离线/临时表归属、保留周期和写入冻结状态。

## 11. 中长期数据库治理路线

- 第一阶段：只读审计、词汇表、枚举注册表、重复数据画像。
- 第二阶段：非破坏性约束设计，先通过代码和监控验证。
- 第三阶段：补 active_key/唯一键/必要索引，建立迁移回滚方案。
- 第四阶段：归档历史导入表和废弃表，保留审计查询能力。
